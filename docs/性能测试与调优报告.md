# 性能测试与调优报告

> 测试日期：2026-09-29 · 对象：`127.0.0.1:8080`（FastAPI + SQLite，单进程 uvicorn）
> 脚本：`.tmp-verify/perf_test.py`（六个阶段）、`.tmp-verify/perf_profile.py`（CPU 剖析）、`.tmp-verify/worker_bench.py`（横向扩展评估）
> 上一轮 `docs/稳定性测试报告.md` 测的是「会不会崩」，本报告测的是「够不够快、上限多少、瓶颈在哪」。

## 一、结论摘要

| 项 | SLA | 实测 | 判定 |
|---|---|---|---|
| 读接口 p95（真实并发 ≤4） | < 200 ms | **219 ms @并发4 / 142 ms @真实峰值（6 连发）** | 基本达标 |
| 错误率 | < 0.1 % | **0 / 400 请求** | 达标 |
| 上传端到端（≤1 MB） | < 3 s | **1.16～1.63 s** | 达标 |
| 内存漂移（3 分钟） | \|Δ\| < 100 MB | **−81 MB** | 达标 |
| 吞吐上限 | —— | **59.2 req/s @ 并发 4** | 见 §3 |

**优化后吞吐上限 +20%，各并发级别 p95 下降 15～35%，冷启动模型加载 −9.7 s，向量化提速 2.06×。**

**一个必须说清的前提**：这台机器 19.8 GB 内存已用 86%（其他应用占 12 GB），只剩 2.7 GB 可用。
模型有 470 MB 常驻，内存吃紧时会被换出、下次访问再换入 —— **尾部延迟（p95/p99）里有相当一部分
是这台机器的内存压力，不是应用本身**。绝对数值偏悲观；但优化前后在同一环境下测得，**相对对比有效**。

## 二、「高峰期」在本应用里到底是什么

先把场景定义清楚，否则测的是虚构的负载。从代码里取出前端实际会打的请求：

| 场景 | 请求构成 | 来源 |
|---|---|---|
| 首屏（登录后） | `auth/status` → `graph` → `files` | `App.vue` → `fileStore.loadPersisted()` |
| 知识库刷新 | **6 个请求并发**：stats / entries / relations / graph / files / imports | `kbStore.refreshAll()` 的 `Promise.allSettled` |
| 系统自检 | 1 个重型请求（12 项检查） | 系统自检页 |
| 上传 | 解析 → 向量化 → 知识锚定 → 关联推理（后台任务链） | `parser.parse_and_extract` |

也就是说，**这个应用真实的「高峰」是 3～6 个并发请求**，不是几百个。
压测里跑到并发 64 是为了找上限，不代表用户会这么用 —— 两个数字都报，避免误判。

## 三、加压曲线与容量结论

同一批端点（8 个读接口混合），每级 120 请求：

| 并发 | 吞吐 (req/s) | p50 | p95 | p99 | 错误 | | 吞吐（优化后） | p95（优化后） |
|---|---|---|---|---|---|---|---|---|
| 1 | 31.4 | 27ms | 71ms | 80ms | 0 | | **35.7** | **59ms** |
| 2 | **49.4** | 27ms | 94ms | 318ms | 0 | | **58.5** | **72ms** |
| 4 | 42.9 | 29ms | 329ms | 486ms | 0 | | **59.2 ← 峰值** | **219ms** |
| 8 | 37.9 | 34ms | 1010ms | 1237ms | 0 | | **54.9** | **771ms** |
| 16 | 37.4 | 71ms | 2208ms | 2721ms | 0 | | **44.5** | **1888ms** |
| 32 | 36.5 | 293ms | 2756ms | 2918ms | 0 | | **47.1** | **2068ms** |
| 64 | 33.9 | 1103ms | 2909ms | 3014ms | 0 | | **41.5** | **2574ms** |

**结论**：

- **吞吐上限 59.2 req/s**，出现在并发 4；超过之后再加并发**吞吐不升反降**，延迟线性上涨。
  这是典型的排队现象：任务是 CPU 密集且在 GIL 下串行，加并发只是让更多请求排队。
- **p95 < 200 ms 只能撑到并发 2～4**；并发 64 时 p95 是 2574 ms（劣化 43×）而吞吐还更低。
- 优化把饱和点从并发 2 推到并发 4 —— 耐压区间变宽了，这才是本轮最有意义的变化。
- 错误率在**所有**并发级别都是 0，没有出现超时或 5xx。

## 四、瓶颈分析（逐层）

### 应用层：单进程 GIL 是硬上限

吞吐在并发 2～4 就封顶、延迟随并发线性上升，说明瓶颈不是 I/O（SQLite 在本地、无外部网络），
而是**一个 Python 进程里的 CPU 串行**。用 `cProfile` 直接剖析端点函数体，最热的两个点：

| 热点 | 位置 | 耗时 |
|---|---|---|
| 行物化 + JSON 反序列化 | SQLAlchemy 结果集（404 行 × 4 个 JSON 列 ≈ 1600 次 `json.loads`） | ~11.5 ms / 次 |
| ORM 实例化 | `kb_graph` 一次物化 969 个 ORM 对象 | ~13 ms / 次 |

这两个都在**每次请求**都要付，且几乎每个 KB 端点都会走到。

### 数据层：查询本身没问题

16 个模型声明的索引**全部存在**（`nodes.file_id`、`links.source_id/target_id`、
`kb_relations.source_entity/target_entity`、`audit_logs.created_at` 等），
`GROUP BY` / `WHERE ... IN` 下推后没有全表扫描，SQLite 查询耗时都在 1 ms 量级。
**数据层不是瓶颈** —— 这一点值得明确写下来，免得后面有人往「加索引」的方向白费力气。

### 依赖层：两处外部依赖在拖慢启动与上传

| 问题 | 实测影响 |
|---|---|
| 模型加载时 huggingface-hub 做一圈版本检查（HEAD 请求） | 模型加载 **13.6 s → 3.9 s** 全在这上面 |
| 前端 `<head>` 里 898 KB 的 CDN 脚本**解析阻塞** | CDN 正常 +0.6 s；**CDN 不可达 +21 s**（实测 TCP 超时 21.07 s） |

### 上传链路：耗时大头是向量化，不是解析

| 文件 | 服务端解析 | 端到端（用户等待） | 节点数 |
|---|---|---|---|
| 102 KB | 107 ms | 1.16 s | 61 |
| 502 KB | 447 ms | 4.67 s | 301 |
| 1003 KB | 914 ms | 1.63 s | 600 |
| 2005 KB | 1062 ms | 1.58 s | 600 |
| 3008 KB | 1832 ms | 3.12 s | 603 |

注意 **502 KB 比 3 MB 还慢** —— 因为耗时跟「节点数」成正比而不是文件大小：
102 KB→61 节点，502 KB→301 节点（没触顶），1 MB 以上都在 600 节点被截断提前收工。
单条文本向量化实测 **6.17 ms/条**，600 节点就是 3.7 s，占端到端的绝大部分。

## 五、已实施的优化与前后对比

### 1. 模型加载跳过线上版本检查（冷启动 −9.7 s）

模型已经在本地下好，但 huggingface-hub 每次加载仍会对每个配置文件发 HEAD 请求
（`adapter_config` / `processor_config` / `preprocessor_config` / `video_preprocessor_config`…），
网络不通时每个还要重试 5 次。改为**命中本地缓存就自动置 `HF_HUB_OFFLINE`**。

- 模型构建：**13.6 s → 3.9 s**
- 附带收益：断网也能启动（不再依赖外网）
- 剩余的 ~15 s 是 `import torch` 本身的固定开销，缩短不了；但它在后台线程里，不阻塞服务就绪

### 2. 推理线程数与批大小（向量化 2.06×）

CPU 推理的线程数是个大旋钮，实测（300 条文本、16 逻辑核）：

| 线程 | 6 | 8（torch 默认＝物理核） | **12** | 16 |
|---|---|---|---|---|
| ms/条 | 7.32 | 6.04 | **4.42** | 5.08 |

「留几个核给服务本身、其余都给推理」最快，**吃满全部核反而因为超订变慢**。
取逻辑核的 3/4（本机 12），批大小 32 → 96。

- **6.17 ms/条 → 3.00 ms/条（2.06×）**；600 节点的向量化从 3.7 s 降到 1.8 s

### 3. 去掉指纹计算里的 ORM 与 JSON 反序列化

索引缓存的内容指纹原本走 ORM 列查询，404 行 × 4 个 JSON 列要反序列化约 1600 次。
改成 `text()` 窄查询 —— **指纹只是判断「内容变没变」，拿库里原样的字符串比对即可，不必解析**。

- 指纹：**11.5 ms → 8.1 ms**（−30%）

### 4. `kb_graph` 只取用得到的列、截断下推到 SQL

原来读完整 ORM 对象、把整段 `definition` 取回来再在 Python 里切 200 字。
改为选定列 + `substr(definition,1,200)` + `count(id)`。
**逐字段比对旧实现，150 个节点 0 处差异、`total_entries` 一致。**

- p50：**68.7 ms → 61.3 ms**

### 5. 前端 CDN 脚本改为 `defer`

898 KB 的第三方脚本放在 `<head>` 且无 `defer` 时是解析阻塞的。
加 `defer` 后不再阻塞解析；`vectorEngine.js` 的 `getTransformers()` 本来就是轮询等
`window.transformers`，**行为不变**。

- 首屏少等 **0.6 s**（CDN 正常）；**CDN 不可达时少等约 21 s**

### 端点级前后对比（单请求 p50，预热后 20 次采样）

| 端点 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| `/api/system/doctor` | 69.2 ms | **51.7 ms** | −25% |
| `/api/summary/mermaid` | 45.6 ms | **34.0 ms** | −25% |
| `/api/kb/files` | 30.5 ms | **23.8 ms** | −22% |
| `/api/kb/stats` | 49.7 ms | **44.0 ms** | −11% |
| `/api/kb/graph` | 68.7 ms | **61.3 ms** | −11% |
| `/api/health` | 16.8 ms | 15.3 ms | −9% |
| **最慢端点 p95** | 85.6 ms | **71.9 ms** | −16% |

同时长尾明显收敛：`/api/kb/stats` 的最大值从 943 ms 降到 52 ms，
`kb_graph` 从 328 ms 降到 69 ms，`mermaid` 从 325 ms 降到 50 ms。

## 七、前端性能

生产构建 `kg-vue3/dist` 合计 **9.77 MB / 94 个文件**：

| 产物 | 体积 | 是否首屏 |
|---|---|---|
| `elk-*.js` | 1434 KB | 懒加载（拓扑布局） |
| `index-*.js`（入口） | **1372 KB** | **是** |
| `cynefin-*.js` | 672 KB | 懒加载 |
| `mermaid.core-*.js` | 611 KB | 懒加载 |
| `index-*.css` | **452 KB** | **是（渲染阻塞）** |
| `cytoscape.esm-*.js` | 433 KB | 懒加载 |
| 7 张背景 webp | 约 2.0 MB | 按需 |

**JS 合计 6.78 MB**。首屏要 1372 KB 入口 JS + 452 KB CSS + 898 KB CDN 脚本 ≈ **2.7 MB**。
代码分割做得不错（elk / mermaid / cytoscape / katex 都是懒加载），
问题集中在**入口块偏大**和**渲染阻塞的 CSS 与 CDN 脚本**。

> 说明：本轮只测了体积与阻塞关系，未做真实浏览器的 LCP/CLS 实测 ——
> 应用停在登录初始化页，且 dev server 的模块化加载不代表生产包，测出来会误导。
> 已在 §九 列为后续项。

## 八、横向扩展评估（多 worker）：能涨，但这台机器付不起

单进程受 GIL 限制，多开 worker 是唯一能真正并行的办法。实测（同端点、每级 120 请求）：

| 配置 | 并发 4 吞吐 | 并发 8 吞吐 | 并发 8 p95 | 内存 |
|---|---|---|---|---|
| 1 worker | 55.1 req/s | 46.9 req/s | 884 ms | ~1.2 GB |
| **2 workers** | **97.5 req/s** | **100.1 req/s** | **275 ms** | ~2.4 GB |

**吞吐 +77% / +113%，p95 −69%** —— 效果显著，因为绕开了 GIL。
但每个 worker 都会各自加载一份 470 MB 模型，**内存翻倍**。

**本轮没有采用**：这台机器 19.8 GB 内存已用 86%，只剩 2.7 GB，
2 个 worker 就要吃掉 2.4 GB（实测已经在跑），再加机器会开始换页、反而更慢。

**建议**：单用户本地使用保持 1 worker（默认）；若换到有 ≥3 GB 空闲内存的机器、
或未来变成多人访问，再加 `--workers 2`。

## 九、优化建议

### 高优先（本轮已完成）
- 前端 CDN 脚本加 `defer`（§五.5）
- 模型加载命中缓存即离线（§五.1）
- 推理线程数与批大小按 CPU 校准（§五.2）

### 中优先（未做，收益明确）
1. **静态资源启用 gzip/brotli** —— 6.78 MB JS 压缩后约 1.5 MB。当前没有任何压缩。
2. **入口块拆分**：1372 KB 的入口大块多半含全量 Element Plus，按需引入 + `manualChunks` 可显著减小首屏。
3. **CSS 瘦身**：452 KB 的 `index.css` 与全量引入组件库有关。
4. **彻底去掉 CDN 依赖**：前端 `vectorEngine.js` 现在只被 `graphValidator.js` / `knowledgeValidator.js`
   使用（客户端算相似度做孤儿收养），而后端已有真语义模型 —— 整条前端向量链路可以考虑删除或改为按需加载，
   这样 898 KB 的第三方脚本和它的可用性风险一起消失。

### 长期
- 若改为多人/远程部署：多 worker + PostgreSQL（SQLite 在多写场景会成为新的瓶颈），
  并把模型改成**独立推理服务**或让 worker 共享，避免每进程一份权重。
- 把「容量与延迟」做成回归门禁（见 §十一），避免这次优化的成果被后续改动吃掉。

## 十一、可加进回归门禁的不变量

本轮已经落进体检的两条（上一轮加的，继续有效）：

```
_init_encoder 必须持有 _init_lock     ← 昂贵惰性初始化必须串行化
load_index    必须持有 _INDEX_LOCK    ← 每请求重建必须缓存化
```

建议再补两条性能门禁（本次未实施，留待后续）：

```
单端点 p95 不得超过基线 1.5 倍        ← 用 perf_test.py --phase baseline 的输出做基线
向量化 ms/条 不得超过 4.5             ← 线程数/批大小被改回去时会立刻暴露
```

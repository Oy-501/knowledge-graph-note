# 登录与认证说明

> 2026-09-29 起生效。旧做法（输入 `backend/.env` 里的管理口令）已被登录页取代。

---

## 一、为什么改

旧做法是让用户在前端输入配置文件里的 `ADMIN_TOKEN`。三个问题：

1. 那是**明文配置项**，输在前端等于把配置文件内容搬进浏览器；
2. 口令没有有效期、不能吊销，改一次要通知所有使用者；
3. 用户得先去翻 `.env` 才知道该输什么 —— 纯粹的摩擦。

现在改为标准登录：密码走 bcrypt 哈希，登录后签发不透明会话令牌，可过期、可吊销、可滑动续期。

---

## 二、凭证与通道

写操作（`POST/PUT/PATCH/DELETE`）现在接受**两种凭证，任一即可，强度相同**：

| 通道 | 请求头 | 要求 | 用途 |
|---|---|---|---|
| 登录会话 | `X-Session-Token` | `role=admin` | 日常使用（登录页自动携带，用户无需关心） |
| 管理口令 | `X-Admin-Token` | 等于 `.env` 的 `ADMIN_TOKEN` | 脚本 / curl / 命令行调试 |

保留口令通道的原因：文档、体检脚本、命令行调试都在用它，去掉会平白打断既有用法；而且它本来就能做全部写操作，所以「支持会话」并没有放宽任何东西。

**日常使用不再需要关心 `ADMIN_TOKEN`。** 前端登录成功后还会主动清掉 localStorage 里遗留的 `kg-admin-token`。

---

## 三、接口

| 方法 | 路径 | 凭证 | 说明 |
|---|---|---|---|
| GET | `/api/auth/status` | 匿名 | 返回 `need_bootstrap` / `registration_open` / `session_ttl_days` / 当前用户 |
| POST | `/api/auth/bootstrap` | 匿名* | 首次初始化，创建首个管理员 |
| POST | `/api/auth/login` | 匿名* | 登录，返回会话令牌 |
| POST | `/api/auth/register` | 匿名* | 注册普通用户（受 `REGISTRATION_OPEN` 控制） |
| POST | `/api/auth/logout` | 登录即可 | 吊销当前会话 |
| GET | `/api/auth/me` | 登录即可 | 当前用户信息 |
| POST | `/api/auth/password` | 登录即可 | 改自己的密码（须验原密码） |

\* 匿名可达，但各自有守卫：`bootstrap` 只在「全库没有任何用户写过密码哈希」时放行，之后永久 403；`register` 受 `REGISTRATION_OPEN` 开关（默认关）；`login` 有失败限流（同一「用户名\|IP」5 分钟 10 次）。

**这三条必须写进 `main.py` 的 `WRITE_GUARD_EXEMPT`** —— 否则登录接口会被写守卫自己拦成 401，造成「永远登不进去」的死锁。

---

## 四、写守卫的判定顺序

```
写请求进来
  ├─ PROTECT_WRITES 关 / 是 GET|HEAD|OPTIONS        → 放行
  ├─ 在 WRITE_GUARD_EXEMPT 里                      → 放行
  ├─ 路径以 /api/admin/ 开头                        → 放行（后台自己有更强的校验）
  ├─ 管理员会话（X-Session-Token，role=admin）
  │  或旧口令（X-Admin-Token）                      → 放行
  ├─ 已登录但非管理员
  │    ├─ 在 WRITE_GUARD_USER_LEVEL 里（登出/改密） → 放行
  │    └─ 其它                                      → 403 admin_required
  └─ 完全未登录                                     → 401 session_required
```

两个容易搞错的点：

- **401 与 403 不能混用。** 「已登录但权限不够」回 403；回 401 会让前端把人踢回登录页，而他明明登录着。
- **`WRITE_GUARD_USER_LEVEL` 是必要的。** 登出与改自己密码只要求「已登录」，否则注册出来的普通账号连退出都做不到。这一条是第一版漏掉的，实测中普通用户登出返回 403 才暴露出来。

---

## 五、首次初始化会做什么

`POST /api/auth/bootstrap` 把**既有 user#1 那一行**直接升格为管理员：

- 文件名下挂在 `user_id=1` 上的文件、节点、笔记**天然归属新管理员**，不需要搬数据、零迁移成本；
- 同时把角色写成 `admin`、写入密码哈希；
- 之后本接口永久 403，不会变成敞开的后门。

---

## 六、配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `SESSION_TTL_DAYS` | `7` | 会话有效期（天）；每次鉴权命中滑动续期 |
| `REGISTRATION_OPEN` | `False` | 是否开放注册入口。默认关（单机个人应用不需要自助注册入口） |
| `PROTECT_WRITES` | `True` | 写操作是否必须登录为管理员 |
| `ADMIN_TOKEN` | `kg-admin` | 兼容保留的第二通道；不用可以置空 |

---

## 七、已知边界

- **令牌存在 localStorage。** 能挡住「别人打开你的浏览器」，挡不住「有人能读你的 localStorage」。彻底解决需要 httpOnly Cookie + CSRF 防护，是一次较大的改造，当前单机场景下没做。
- **限流是单进程内存实现**（`services/security.py` 的滑动窗口），多进程部署时要换共享存储。
- **改密会吊销全部会话**（含当前会话），前端收到 `re_login` 后回登录页。这样做是为了让「改密」真正起到「把别处的登录踢下线」的作用。
- **普通用户能登录、能看数据，但不能写。** 角色目前只能改数据库，后台没有角色管理界面。

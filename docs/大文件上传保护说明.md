# 大文件上传保护说明（为什么之前会崩、现在怎么防）

> 现象：上传大文件（几 MB 到几十 MB 的笔记/语料）时，"网站崩溃" ——
> 请求卡死、页面转圈、图谱视图卡住甚至标签页无响应。

---

## 一、根因（四层叠加，任何一层都能把服务拖死）

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 1 | `POST /api/files/upload` | `await file.read()` 把**整个文件读进内存**，无任何大小限制 | 几十 MB~GB 级上传直接撑爆内存，进程被系统杀掉 → 站点整体不可用 |
| 2 | `parser.parse_and_extract` | 逐行抽取**无行数/知识点上限** | 几万行文档产出上万节点，后续每一步都在万级规模上跑 |
| 3 | `inference.infer_links_batch` | **O(新节点 × 既有节点)**，且 `check_corpus_bridge_score` **每对比一次就查一次数据库** | 3000×3000 = 900 万次「Python 打分 + SQL 往返」，请求永不返回；SQLite 写锁被长事务占住 → 所有接口排队 → 表现为"崩了" |
| 4 | `embed_to_db` | 每个节点一次 `SELECT` | 几千次查询，进一步放大耗时 |
| 5 | 前端 `GraphCanvas` | D3 力导向渲染**全部**节点与标签，无降级 | 几千节点时主线程长时间占满，标签页卡死 |

---

## 二、现在的分层防护

### 1) 上传入口（`api/files.py`）

- **限额流式读取**：`await file.read(limit + 1)`，一超过上限立刻返回 **413**，超出部分根本不读进内存：

  > 文件超过 20MB 上限（当前 ≥ 20.0MB）。请拆分成多个较小文件分批上传，或先精简内容。

- **二进制拦截**：前 8KB 含 NUL 字节 → **415**，提示先另存为文本（PDF/Office/压缩包这类文件进解析只会产出垃圾节点）。
- 本地工作区同步（`/files/sync`）同样有体积上限。
- 新增 `GET /api/files/limits`：把上限暴露给前端，**前后端阈值同源**。

### 2) 解析（`services/parser.py`）

- `MAX_PARSE_LINES = 20000`：超出只解析前 2 万行；
- `MAX_NODES_PER_FILE = 600`：知识点到顶即停止抽取；
- 截断原因写入 `files.parse_note`，前端文件列表显示 **⚠ 已截断** 徽标（hover 看详情）：
  > 文件较大：仅解析前 20000 行；知识点已达上限 600 个，其余已忽略；建议拆分成多个较小文件分别上传，解析更完整

### 3) 关联推理（`services/inference.py`）—— 最关键

| 保护 | 做法 |
|---|---|
| 知识库改内存索引 | 一次 `load_index` 得到别名表 + 关系邻接表，桥接打分变成内存集合运算，**消除每对一次的 SQL 往返** |
| 候选集剪枝 | 既有节点 > 300 时，只与「实体/关键词有交集」的节点比较（倒排索引），无交集直接不连（也是"知识边界"的体现） |
| 配对数预算 | `LINK_PAIR_BUDGET = 120000` 对，超了提前收工并记日志 |
| 时间预算 | `LINK_TIME_BUDGET_S = 20` 秒，到点收工 |
| 输出限流 | 每节点最多保留 `MAX_LINKS_PER_NODE = 8` 条最强连线；单轮最多 `LINK_OUTPUT_LIMIT = 4000` 条 |
| 批量写库 | `embed_to_db` 由「每节点一次 SELECT」改为一次 `IN (...)` 批量查回填 |

`/api/knowledge/infer`（前端上传后调用的推理接口）同样受这些预算约束，并额外限制节点数。

### 4) 文件/节点级联（`services/kb_link.py`）

- 文件两两比较：`MAX_FILES_FOR_LINKING = 150` 个文件、`MAX_FILE_LINK_SECONDS = 15s`；
- 知识锚定连线：节点超过 `MAX_NODES_FOR_KB_LINK = 4000` 时只处理锚定最丰富的一批。

### 5) 前端（`FileUploader` / `fileStore` / `GraphCanvas`）

- **上传前拦截**：按后端上限校验体积与类型，超限文件直接跳过并给出建议（不再整份传到一半才失败）；
- 拖拽区常驻提示：`单文件 ≤ 20MB · 仅纯文本（PDF/Office 请先另存为文本）`；
- 大文件解析时进度文案提示可能需要 1-2 分钟，轮询超时放宽到 3 分钟；
- **渲染降级**：节点 > 600 时只给度数最高的 260 个节点画文字标签；> 1200 时降到 120 个并省略分组标签；节点 > 800 时降低斥力、加快力导向收敛；
- 图谱 > 1200 节点时提示一次：建议用「分组 / 风格筛选」聚焦范围。

## 三、实测数据（1.09MB / 16000 行 / 4000 个候选知识点）

| 场景 | 结果 |
|---|---|
| 上传 1.09MB 文件 | 上传 0.19s |
| 解析 + 知识锚定 + 四维关联 | **0.68s**（节点按上限收敛到 200 个，`parse_note` 正确记录截断） |
| 第二个同主题大文件 | 1.23s |
| 21MB 文件 | **HTTP 413，0.19s 拒绝**（不读进内存） |
| 二进制文件（伪装 .pdf） | **HTTP 415**，提示转文本 |
| 极端压力：600 新节点 × 800 既有节点（名字不同但共享关键词，走完整四维打分） | 48 万潜在配对 → **2.02s** 收工（比较 12 万对后触发预算），最终收敛为 3208 条连线 |

作为对比：改造前同样规模需要 12 万次数据库查询 + 12 万次完整打分，且最终会写出 12 万条连线 —— 这正是"崩"的来源。

## 四、可调参数（`.env` 或环境变量）

```ini
MAX_UPLOAD_MB=20            # 单文件上传上限
MAX_PARSE_LINES=20000       # 单文件最多解析行数
MAX_NODES_PER_FILE=600      # 单文件最多知识点数
MAX_LINK_CANDIDATES=300     # 每个新节点最多比较的既有节点数
LINK_PAIR_BUDGET=120000     # 单次关联推理最大配对数
LINK_TIME_BUDGET_S=20       # 单次关联推理时间上限（秒）
MAX_LINKS_PER_NODE=8        # 每个节点最多保留的连线数
LINK_OUTPUT_LIMIT=4000      # 单次关联推理最多产出的连线数
MAX_NODES_FOR_KB_LINK=4000  # 知识锚定连线最多处理节点数
```

> 想把上限调大：先把 `MAX_NODES_PER_FILE` 提到 1500、`LINK_TIME_BUDGET_S` 提到 60，
> 观察 `/api/health` 是否仍然秒回。**不建议同时放大配对数预算与候选剪枝门槛**，
> 那会把 O(n²) 重新放回来。

---

## 五、使用建议（比调参数更有效）

1. **按主题拆文件**：单文件控制在 2000~5000 行、5MB 以内，解析完整且关联更准；
2. **长文档先结构化**：`## 概念名` + 一句定义，抽取质量与关联质量都会显著提升（见「图谱总结」里的噪音提示）；
3. **用分组隔离**：不同领域分到不同分组，既减少无谓比较，也让图谱可读；
4. **不要上传 PDF/Office/压缩包**：系统只解析纯文本，先另存为 .md/.txt/.csv；
5. 上传后若看到 **⚠ 已截断**，说明该文件没被完整解析，建议拆分后重传。

---

## 六、仍然存在的限制（如实说明）

- 解析在 `BackgroundTasks` 的线程池里跑，**单进程 uvicorn** 下多个大文件会排队；生产部署建议 `--workers 2` 或把重型解析交给独立 worker（RQ/Celery）。
- SQLite 是单写库，超大图谱的全量重建（`/api/graph/rebuild`、`/kb/rebuild`）仍会占用写锁；建议在空闲时执行，或切换到 PostgreSQL（`DB_MODE=postgres`）。
- 前端力导向渲染的**上限**在数千节点级别；再大应依赖「分组 / 筛选 / 局部图谱」而不是全量渲染。

| 结论 | 说明 |
|---|---|
| **全套功能可用** | 上传、异步解析、实体抽取、连线推理、知识库锚定、图谱渲染、候选判定、审计留痕，逐项实测通过 |

## 三、功能实测（12 篇代表样本 + 1 篇界面上传）

样本：MSFT 取最短与最长各一篇（`TranscriptFY14Q4`、`TranscriptFY15Q4`），HotPotQA 取前 10 篇非空 + 1 篇空文件。

### 3.1 成功路径

| 环节 | 实测结果 |
|---|---|
| 上传 | 12 篇全部 200；返回 `status=parsing`（**异步解析**，不是同步返回节点数） |
| 解析 | 12/12 最终 `status=done`；单篇 3～49 个节点 |
| 抽取 | 170 个节点、171 条候选知识点（每节点一条候选，符合设计） |
| 连线 | 564 条，全部 `auto_generated` |
| 知识库锚定 | 覆盖 10/12 篇（83%）；文件级关联 17 条、节点级锚定 10 条 |
| 候选判定 | 133 条 `pending`（进人工队列）、38 条 `reject`、**0 条自动采纳** |
| 联网判定 | 134 条 `ok`、37 条 `unavailable`（联网校验真的执行了） |
| 审计 | 198 条记录 |
| 界面 | 图谱页渲染 170 节点 / 563 连线；知识库页统计与接口逐项一致 |

单篇节点数（前几名，反映抽取量级）：

## 四、实测发现的问题（按严重程度）

### 4.1 语义链路降级为 TF-IDF —— 影响最大

后端日志：

```
WARNING | app.services.vector_engine:_init_encoder - Failed to load transformers,
          using TF-IDF fallback: No module named 'sentence_transformers'
```

`requirements.txt` 里声明了 `sentence-transformers==2.2.2`，但当前环境**没有装**。后果是语义相似度用 TF-IDF 计算 —— 它按词频重合度衡量，对「换个说法说同一件事」完全无能为力。本批语料是英文，而系统面向中文知识库，TF-IDF 的效果比在中文语料上更差。

**要恢复设计中的语义能力，需要安装该依赖：**

```
py -m pip install sentence-transformers==2.2.2
```

（体积较大且首次使用要下载模型，装之前建议确认磁盘与网络。）

### 4.2 题目 CSV 不含答案与依据 —— 问答链路无法自动评估

README 声称每行是「问题 + 答案 + 依据文档 id」，实际四个 CSV 的列都只有：

```
HotPotQA Filtered Questions.csv     → question_id, question_text
MSFT Single Transcript Questions.csv → question_text, question_id
```

没有 `answer` / `evidence` / `doc_id` 列。而且 HotPotQA 的 `question_id` 是 40 位哈希，文件名是 `test_N`，**两者无法配对**。

所以本报告只能验证「文档被正确解析并进入图谱」，**不能**验证「给定问题能否检索到正确文档」这类检索质量指标。要做后者，需要另外提供带标注的问答集，或按文件名与题号自行建立映射。

### 4.3 英文语料落在知识库边界之外 —— 不是缺陷，但要知道

系统的关联建立在**知识库**之上（知识边界是刻意设计：未被知识库覆盖的内容不参与关联）。本项目知识库是 404 条中文软件工程概念，因此：

- 英文人名、电影、财报术语**基本锚定不上**（HotPotQA 的 `Adam Collis`、`Ed Wood` 之类）
- 仍有 10/12 篇被覆盖、10 条节点级锚定，命中的是语料里出现的技术词（`RAG`、`SQL`、`OS`、`MSFT` 等）
- 结论：**这批语料适合测「链路通不通」，不适合测「关联准不准」**。要测后者应该用中文技术文档。

### 4.4 抽取噪声：转录里的人名被当成实体

41 篇 MSFT 转录里，说话人姓名是**全大写**行（`CHRIS SUH:`、`AMY HOOD:`），抽取器把它们当成了实体。图谱里因此出现大量 3～4 个字母的节点（`WALTER`、`HAMP`、`BJ`、`AMY`、`KARL`、`RICK`、`BRAD`…）。

判断依据：判定环节把它们多数判成了 `reject`（38 条中大头是这类），阈值机制**起了作用**；但节点仍然进了图谱，视觉上较吵。

### 4.5 自动采纳为 0

171 条候选里没有一条达到自动采纳阈值（`VERDICT_AUTO_ACCEPT=0.80`），最高分是 `RAG` 0.83 —— 但它仍是 `pending`，说明还有其它条件在把关。结果是 **133 条要人工审**。对 12 篇文档来说这个量偏大，实际使用中会堆积。

## 五、怎么复现

```bash

  py -m uvicorn app.main:app --host 127.0.0.1 --port 8080

# 2. 上传（脚本读 backend/.env 里的 ADMIN_TOKEN 作为凭证）
py .tmp-verify/bench_upload.py 8080
```

```bash
cd backend
SQLITE_PATH=./split_test.db DB_MODE=sqlite SPLIT_TARGET_LINES=80 SPLIT_TARGET_CHARS=8000 \
  py -m uvicorn app.main:app --host 127.0.0.1 --port 8092
```

（本批语料在默认阈值下不会分片，所以分片链路这次没有被覆盖到。）

## 六、给后续的建议

1. **装 `sentence-transformers`** —— 否则语义关联一直跑在降级模式上，这是当前最大的能力缺口。
2. **✅ 已补：带标注的问答集** —— `test_data/k12_eval/` 已提供「问题 + 答案 + 出处文档名」共 577 条，可正式评估检索质量（详见第七节）。
3. **测关联质量请用中文技术文档** —— 英文语料与当前知识库不在同一知识域（K12 数学语料已属中文，可作为过渡）。
4. **如果要用英文语料**，需要在知识库中补英文实体与别名，否则它们始终落在知识边界之外。
5. 全量上传 5,491 篇是个大工程（本篇 13 篇约 1 分钟解析），建议先按需抽样。

## 七、检索质量评估补强：K12 可评估测试集（新增）

针对 4.2 节指出的「题目 CSV 不含答案与依据 → 问答链路无法自动评估」缺口，2026-09-29 补充了 **K12 可评估测试集**（`test_data/k12_eval/`）。这是唯一能在 GitHub 直取的、自带「问题 + 答案 + 依据文档」映射的中文数据集（上游：`haolpku/K12-KGraph`，NeurIPS 2026 教育知识图谱基准；CMU/HotPotQA 官方与 HuggingFace 源实测均连接超时不可达）。

### 7.1 数据规模与结构

| 内容 | 数量 | 说明 |
|---|---|---|
| `docs/KG_*.md` | 509 篇 | 每篇一个知识点（小学数学：时间/分数/图形/加减法），含定义 + 提问示例，可直接上传建图谱 |
| `questions_with_answers.csv` | 577 条 | `question` + `answer` + `expected_doc`（应定位文档名）+ `kind`（node/edge） |

### 7.2 评估方法（三步）

1. **上传**：将 `docs/` 全部 509 篇上传，系统完成切割 + 语义关联 + 图谱构建；
2. **提问**：对每条 `question` 发起问答/检索；
3. **判定**：系统返回的内容是否来自 `expected_doc` 对应文档 → 命中记 1，否则记 0。

### 7.3 可计算指标

| 指标 | 算法 | 说明 |
|---|---|---|
| **文档定位命中率** | 命中数 / 577 | 核心指标，判断「能否找到正确答案所在的文档」 |
| **答案语义匹配** | 系统回答与 `answer` 的余弦相似度 | 需先装 `sentence-transformers`（见 4.1） |
| **跨文档多跳能力** | 仅统计 `kind=edge` 的题目 | 这类题需结合两个知识点，直接验证「语义桥梁」与跨文件关联 |

### 7.4 附带价值

- 语料内存在 `KG_时间单位的换算.md` 与 `KG_时间单位换算.md` 两个语义几乎相同的文档，可验证系统**能否区分语义相近文档**（图谱质量的判别性指标）；
- 全部为中文，落在当前知识库（中文软件工程概念）的同语言域，比 4.3 节英文语料更适合测「关联准不准」；
- 知识点粒度与笔记场景一致（每篇几百字符），不会触发分片，聚焦检索链路本身。

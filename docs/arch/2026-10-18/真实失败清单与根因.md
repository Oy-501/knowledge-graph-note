# 真实失败清单与根因判断

上一轮列的 10 条是**注入**的失败（用来证明测试有效）。
这里列的是开发过程中**真实踩到**的失败，以及其中几条「看起来通过、实际无效」的缺陷。

## F1 断言读到陈旧值 —— 会话缓存

- **现象**：`test_rerun_does_not_override_human` 首次运行失败
  `AssertionError: assert 'auto' == 'human'`
  而 HTTP 的裁决请求返回 200，说明接口确实改成功了。
- **根因**：SQLAlchemy 的 identity map。测试 session 已加载过这个候选对象，
  HTTP 请求在**另一个 session** 里改并提交；测试 session 再次 `query` 时命中
  identity map，返回的是**同一个 Python 对象**且不会刷新它的属性 —— 于是读到旧值。
- **现场验证**（两个真实连接的文件库）：

  ```
  1) s1 首次读取： auto
  2) s2（另一个连接）已改为 human 并提交
  3) s1 再次查询： auto        <- 陈旧
     是同一个 Python 对象吗： True
  4) expire_all 之后： human    <- 正确
  ```

  注意 `again is first` 为 True，确认是 identity map 命中，不是事务快照。
- **修复**：断言前 `db.expire_all()`。
- **类别**：测试夹具 / 会话隔离。

> 附带一个坑：第一次想验证这条时用了内存库 `sqlite://`，
> 它默认同线程共享连接，两个「session」其实是同一个 —— 什么都测不出来。

## F2 补丁只打一处，抓不到回归 —— 测试看着绿，实际是瞎的

- **现象**：把批量入库改回「每条都重建关系」，`test_bulk_ingest_rebuilds_relations_once` **仍然通过**。
- **根因**：同一个函数在两个模块里是**两份引用**。
  `knowledge_verifier` 是在函数体内 `from kb_index import ...`（运行时才取模块属性），
  `admin` 是模块级 `from ... import`（导入时就绑定了一份）。
  只给 `kb_index` 打补丁换不掉 `admin` 里那份，于是计数始终为 1。
- **修复**：两处都打同一个计数函数。
- **类别**：测试有效性缺陷。**它不是运行失败，是"该红的时候没红"** ——
  比 F1 危险得多，因为它不会报错，只会安静地失效。
- **发现方式**：是靠反向验证（故意破坏看红不红）发现的，不是跑出来的。

## F3 变异矩阵误判「10/10 漏网」—— 度量工具本身错了

- **现象**：矩阵第一版输出所有破坏都"没抓到"，但同一份输出里 FAILED 行明明都在，
  被抓到的用例名也解析出来了 —— 自相矛盾。
- **根因**：pytest 在 `-q` 下被 subprocess 捕获时**不输出统计行**，
  脚本解析 `(\d+) failed` 落空，`failed` 恒为 0。
- **修复**：判据改成**数 FAILED 行的条数**。
- **类别**：度量工具缺陷。
- **教训**：证据自相矛盾时先怀疑度量工具。若当时信了这个结果，
  我会去改一堆本来正确的测试。

## F4 新接口 404 —— 进程残留

- **现象**：`/api/knowledge/node/1/notes` 返回 404，但路由就在 `knowledge.py` 里。
- **根因**：旧的 uvicorn 进程仍占着 8080，跑的是**改动前的代码**。
  之前用 `pkill -f "uvicorn app.main:app"` 没清干净（子进程与匹配方式的问题）。
- **修复**：`netstat` 找到 LISTENING 的 PID，`taskkill /F`，再重启。
- **类别**：环境 / 进程残留。这类失败最容易误判成"代码写错了"。

## F5 代码笔误（构建期会炸，但测试不会报）

| 笔误 | 后果 |
|---|---|
| `import { ElMessage } from 'electron-tip'` | 模块不存在，应为 `element-plus` |
| `themeStore.js` 的 `apply()` 里留了 `set root vars` 占位 | 方法不完整 |
| test 文件开头写成 ` import json`（多一个空格） | SyntaxError |
| main.css 注释里混入非中文字符 | 编码噪声 |
| 模板里出现「ここ是标题」 | 混入日语 |

- **类别**：笔误。**它们是被构建与自查发现的，不是被测试发现的** ——
  这本身说明测试管不到这类问题，构建与静态检查才是那道防线。

## 分类与判断

| 类别 | 条数 | 危险程度 | 为什么 |
|---|---|---|---|
| 测试有效性缺陷（该红不红） | 1（F2） | **最高** | 不报错，安静失效，只能靠反向验证暴露 |
| 度量工具缺陷 | 1（F3） | 高 | 会让你对着错误的结论去改正确的代码 |
| 测试夹具缺陷 | 1（F1） | 中 | 会红，能发现，但根因不好一眼看出来 |
| 环境 / 进程残留 | 1（F4） | 中 | 会红，但容易误判成代码 bug |
| 代码笔误 | 5（F5） | 低 | 构建期就会炸，测试管不到也不必管 |

**最值得警惕的是 F2 与 F3**：它们都不是"测试失败"，而是
**测试通过了却没在测东西**。前者让守护失效，后者让证据失真。
这两条都是靠"故意破坏看红不红"发现的 —— 也就是变异矩阵存在的理由。

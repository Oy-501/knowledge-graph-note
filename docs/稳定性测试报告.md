## 1. 怎么测的

原则：**测试脚本自己管进程**。不假设服务已经跑着 —— 最值钱的发现在冷启动那几秒。

```
① 冷启动并发   kill 端口 → 清空日志 → 启动 → 等 /health 200 → 立刻 24 并发打 /api/system/doctor
              → 数日志里「模型被加载了几次」+ 读进程峰值内存
② 稳态压测     11 个端点按权重混合，400 请求 / 24 并发 + 内存漂移；另跑一轮 3 并发做对比
③ 边界与模糊   20 个用例 + 分页夹取实测 + 5 个原始报文（绕开 urllib 的自我校验）
④ 恢复性       压测后 /health、自检、审计里有无未捕获异常
⑤ 前端         首页、入口脚本、20 次采样
⑥ 上传链路     61KB / 604KB / 3MB 文本 + 二进制冒充 + 3 路并发上传 + 悬空引用 + 清理
```

进程内存用 `psapi.GetProcessMemoryInfo`（`ctypes`）直接读，不依赖 psutil。
关键判据不是「有没有报错」，而是**初始化次数与峰值内存**——这两项坏了也不报错。

## 2. P0：模型被并发重复加载（竞态）

### 现象

冷启动 24 并发 → 日志里 `Loading vector model` 出现 **24 次**，
进程峰值 **8097 MB**，最慢请求 **67 秒**。

### 根因

`vector_engine._init_encoder()` 是「先检查标志、再加载、最后置标志」：

```python
if _initialized:      # ← 检查
    return
model = SentenceTransformer(...)   # ← 耗时十几秒，期间毫无保护
_initialized = True   # ← 置位太晚
```

加载期间到达的请求**全部通过检查**，各自加载一份 470MB 的模型。
这个写法在降级路径（纯 CPU、瞬时）下看不出来，装了模型之后窗口变成十几秒，必炸。

### 修复

双重检查 + 锁（锁外快速判断保住热路径，锁内再判断一次）：

```python
if _initialized:
    return
with _init_lock:
    if _initialized:
        return
    _load_encoder()
```

外加**启动期后台预热**（daemon 线程，不阻塞服务就绪）：
把首次请求的十几秒挪到启动期，否则「系统自检」点下去半天没反应，很容易被当成服务挂了。

`prepare(force=True)` 也纳入同一把锁 —— 否则「清空编码器重试」可能插在别的线程正在用它的时候。

### 验证

| | 修复前 | 修复后 |
|---|---|---|
| `Loading vector model` 次数 | 24 | **1** |
| 峰值内存 | 8097 MB | **1749 MB** |
| 加载耗时（日志时间戳） | — | 11.7 s（单次） |

## 3. P1：知识库索引每个请求都重建

### 现象

24 并发下稳态压测，`/api/kb/*` 全线退化：

| 端点 | 单请求（预热） | 24 并发 p50 |
|---|---|---|
| `/api/kb/stats` | 183 ms | **9598 ms** |
| `/api/kb/graph` | 96 ms | 5403 ms |
| `/api/kb/entries` | 55 ms | 5019 ms |
| `/api/kb/files` | — | 1820 ms |
| `/api/admin/overview` | 46 ms | 1901 ms |

吞吐被压到 **7.0 req/s**（`/api/health` 单个只占 15ms，说明不是网络或调度问题）。

### 根因

两处「读起来很自然」的写法：

1. `kb_index.load_index(db)` **完全没有缓存**，每次调用都读全表（404 条目 + 2631 关系边）
   并重建别名表与邻接表 —— 约 60 ms。而它几乎被每个 KB 端点调用。
   24 个请求 = 24 次重建，在 GIL 下排队。
2. `kb.py` 里为了数个数把**整张关系表读进内存**：
   `for r in db.query(KbRelation).all(): counter[r.source_entity] += 1`（出现 3 处）。
   `kb_graph` 更是把 2631 条边全读出来再在 Python 里逐条判断端点是否在当前页。

### 修复

- `load_index` 加**进程级缓存**，键用**内容指纹**而不是计数指纹：

  > 刻意不用 `count(*) + max(id)`：那种计数级指纹对「改了一条已有条目」（改别名、
  > 改定义）不敏感，缓存会一直供旧数据，而且这种错极难发现。内容级指纹约 12 ms，
  > 仍比全量重建便宜一个量级，且**任何写路径都自动生效**，不需要在每个写入口手动失效 ——
  > 那才是容易漏的地方。

  锁的范围包含「读指纹 + 构建」，并发都未命中时只让一个线程构建。
  （`KbIndex` 构造完只读 —— 已用 AST 确认所有 `self` 赋值都在 `__init__` 里 —— 可安全跨线程共享。）

- 聚合与过滤下推到 SQL：`GROUP BY` 代替「读全表再数」，`WHERE ... IN (...)` 代替 Python 筛选。

### 但「变快了」不够，必须验证「结果等价」

SQL 分组 / 过滤下推最容易悄悄改掉口径。`.tmp-verify/verify_perf_fixes.py`
把新旧两种算法放在同一份数据上逐项比对：

```
[OK] 来源计数完全一致 — 2 类 · KB 404 条
[OK] 每实体关系数完全一致 — 404 个实体 · 合计 2631 条边
[OK] 边集合完全一致（顺序无关）— 节点 200 · 边 1176 条
[OK] 反向验证：不设过滤时边数应更多（证明比对有效）— 全表 2631 条 vs 页内 1176 条
[OK] load_index 两次调用返回同一实例（缓存生效）
[OK] 改一条已有条目的别名后指纹变化（计数级指纹会漏掉这种）
[OK] 缓存索引与全新构建的索引：统计 / 别名表 / 邻接表 全部一致
```

### 效果

| 端点 | 修复前 24 并发 p50 | 修复后 |
|---|---|---|
| `/api/kb/stats` | 9598 ms | 1998 ms |
| `/api/kb/graph` | 5403 ms | 215 ms |
| `/api/kb/entries` | 5019 ms | 34 ms |
| `/api/kb/files` | 1820 ms | 20 ms |
| `/api/admin/overview` | 1901 ms | 36 ms |
| `/api/profile/overview` | 1634 ms | 15 ms |

`/api/kb/stats` 剩下的 ~2s 是 **CPU 侧任务在 GIL 下排队**，不是接口本身慢：
它现在每次只花 ~12ms（指纹）+ ~2.6ms（其余查询）。真实并发（3 路）下 p50 = 84 ms。

## 5. 压测并发 vs 真实并发

24 并发是压力测试，**不代表用户实际并发**。同一套端点用 1~3 并发再跑一遍：

| | 24 并发 | 3 并发 |
|---|---|---|
| p50 | 35 ms | 31 ms |
| p95 | 2077 ms | **151 ms** |
| p99 | 2221 ms | 305 ms |
| max | 2499 ms | 445 ms |
| 吞吐 | 54.1 req/s | 60.4 req/s |

差别大的端点（`/api/kb/stats`、`/api/summary/mermaid`）就是「CPU 侧任务重」的端点：
它们的实际耗时只有 ~12ms / ~35ms，长的部分是在 GIL 下排队。真实使用下不需要优化。

**冷启动的 56.6 秒要单独说明**：这是「24 个并发请求同时冷启动」的极端场景。
日志时间线显示模型本身只加载了 11.7 秒，剩下的是
① 24 个线程抢 GIL，把预热的 `import torch`（几秒的 CPU 密集操作）推迟了约 20 秒；
② 加载完成后 24 个 `doctor` 依次跑完。
空载时预热在启动后十几秒内就完成，用户第一次点击（前端还要加载几秒）通常不会撞上。
换句话说：**这是压测制造的排队，不是每次重启都要付的代价。**

## 8. 落进体检的不变量

新增两条（`语义向量接线` 项内，AST 断言），防止以后再退化：

```
_init_encoder 必须持有 _init_lock      ← 昂贵惰性初始化必须串行化
load_index    必须持有 _INDEX_LOCK     ← 每请求重建必须缓存化
```

反向验证：把 `with _LOCK:` 改成 `if True:` → 两项都如实报 error；还原后回到 ok。
**体检项如果永远绿灯，就等于没有。**
